# Jali per-user tools, credentials and execution isolation

Verified 2026-11-10 against owning source. Planning only; no logins, tokens, credentials, running workspaces or production configuration inspected or changed.

## Answer

**The confirmed shared-runtime design is not safely implementable as configuration only in Felix v0.6.1 or current origin/main.** Separate API Contacts/keys provide HTTP resource ownership. They do not select separate downstream JALA OAuth credentials, isolate broad harness tools, or isolate the filesystem that produces artifacts. This is a deployment/integration blocker for the proposed multi-user JALA read/write service, not a reason to substitute a shared privileged JALA account.

Minimum choices are (a) separate execution/runtime boundaries per JALA user, retaining Felix API ownership and adding app/OAuth integration, or (b) implement a tenant-aware tool broker **and** execution/storage isolation in Felix or an external execution service. Merely adding per-Contact token storage or separate MCP server registrations is insufficient for the confirmed broad-tool scope. These are design options, not user decisions.

## What the existing Contact boundary actually enforces

`F/src/server/agents-api/sessions.ts:25-29` (`ownedSession`) derives the thread key from authenticated `apiContact.user_id` and the supplied session ID, then checks its conversation owner. Lists similarly filter by Contact. Input sender identity is constructed from that authenticated Contact, not message text. `F/src/server/agents-api/files.ts:33-49` resolves artifact lists/downloads through this ownership check. This is a useful real HTTP boundary and should remain in the app design.

`F/src/channels/api/artifacts.ts` (`outputFile`, `publishReply`, `artifactContent`) restricts publication to the session outputs directory, checks path/symlink/hardlink/size invariants and snapshots/verifies downloads. It does **not** establish provenance of output contents: a harness with access to another user's records can copy those records into its own outputs and publish them legitimately. HTTP download authorization cannot repair such earlier contamination. That consequence is an inference from shared harness filesystem access and the publication mechanism, not a demonstrated live leak.

## MCP credentials and tool visibility are shared by server

- `F/src/mcp/server-registry.ts:12-19,64-96,242,294-295`: credentials are transport-shaped `{headers, env}`, held in a process-local map keyed by **MCP server ID**. Server registration has no Contact/user credential binding. Credentials are intentionally absent from persisted server records. This registry is not a durable per-user OAuth token/refresh store.
- `F/src/mcp/server-manager.ts:79-106,301-320`: manager obtains `getCredentials(server.id)`, creates/replaces one upstream per server, and supplies those headers/env to that transport. No authenticated Contact is an input to credential resolution.
- `F/src/mcp/relay.ts:193-215` records requester ID/source/owner flag in ephemeral access. But `visibleCapabilities():238-263` selects globally enabled/ready/connected server capabilities without requester filtering. `callTool():380-407` uses the global `upstreams.get(entry.server.id)` and forwards arguments/meta; it does not resolve a requester-specific bearer credential or pass a trusted user identity to the upstream for authorization.
- `F/src/core/turn-runner.ts:88-103,238` and `F/src/mcp/harness-access.ts` bind/revoke an ephemeral relay token for a turn. `F/src/index.ts:353-373` creates a single registry/manager/relay and opts Codex, Claude Code and OpenCode into process-scoped gateway configuration. Antigravity is excluded because no documented process-scoped MCP boundary exists. **Process-scoped relay access is distinct from user-scoped upstream credentials.**

Consequently, registering one JALA MCP server per user does not isolate users: current discovery/call selection exposes all enabled servers to all gateway-authorized turns. Rotating a single server's headers for each turn is also unsafe as a proposed concurrency/reconnection design and is not a supported Contact-scoped configuration contract. A prompt saying which JALA user is active does not change these code paths.

## Harness and artifact workspace are not tenant sandboxes

`F/src/config.ts:59,314` constructs one configured workspace. `F/src/adapters/codex/index.ts:163-208` runs each turn with `cwd: cfg.paths.root`, inherited process environment and configured provider environment; shared Codex auth state lives under that workspace (`projectCodexOAuthAuth`). Its execution arguments use `--dangerously-bypass-approvals-and-sandbox` (`:54-57`, `buildCodexTurnArgs`). Claude Code uses `--dangerously-skip-permissions`, the configured workspace and inherited environment (`F/src/adapters/claude-code/index.ts:416-446,464-512`). OpenCode executes against `cfg.paths.root` with process/config environment (`F/src/adapters/opencode/index.ts:409-425,636-696`). These paths do not create per-Contact containers, OS users, filesystem mounts or credential namespaces.

Skills and Felix permission instructions govern behavior, but do not turn this shared shell/filesystem into an enforced tenant boundary. Model-provider credentials for the independently configured 9Router gateway are also different from JALA user OAuth credentials; selecting `openai/gpt-6-luna` does not supply the missing isolation. No claim is made that every tool is exploitable; the architecture lacks the required enforcement for the broad multi-user capability target.

## Existing app login versus JALA MCP OAuth

`N/utils/auth.ts:18-54` requests ordinary JALA OAuth login, maps profile `data.id`, and propagates the access token into JWT/session callbacks. `N/app/api/[[...paths]]/route.ts:8-30` uses server-side `auth()` and forwards that token to ordinary JALA API routes. Neither establishes the additional MCP resource binding, per-user Felix mapping or stream proxy.

The current backend owning source requires an MCP-authorized OAuth2 token:

1. `B/config/mcp.php:4-13`, `B/app/Http/Middleware/McpResourceBinding.php:12-34`, and `B/app/Http/Controllers/Auth/McpOAuthController.php:18-47` require the intended MCP resource for MCP authorize/token requests and bind issued access-token records to it. Production default resource is `https://app.jala.tech/mcp`.
2. `B/app/Services/Mcp/McpAuthCodeGrant.php` enforces S256 PKCE, client/redirect-bound authorization code exchange and uses the authorized `payload.user_id` when issuing tokens. `offline_access` controls refresh-token issuance. `McpScopeRepository.php` admits only MCP read/write and offline scopes for this flow.
3. `B/app/Http/Controllers/Auth/AuthorizationController.php:31-61` uses the currently authenticated JALA user, shows consent for requested scopes, and may reuse an already valid matching grant. The ordinary first-party shortcut explicitly excludes MCP. Existing login can therefore supply authenticated identity for an MCP consent flow, but is not itself MCP consent or a convertible MCP token. An app callback still needs state/PKCE/session binding and must ensure the grant belongs to the intended app user; this connection is additional integration.
4. `B/app/Http/Middleware/McpBearerAuthenticate.php:14-33` requires nonrevoked resource-bound token record and an authenticated API user. `B/app/Http/Controllers/Api/McpController.php:70-78,148-151` checks required MCP scope and dispatches as `request->user()`. `B/app/Services/Mcp/McpControllerAdapter.php:53-70,90-121` sets that user on internal requests, dispatches existing routes and invokes declared Gates; existing route/controller policies remain relevant. The protocol grants allowlisted capability, not extra farm/admin privileges. This bounded trace is not an exhaustive policy audit of every registered tool.

### Documentation/source discrepancy: registration

`B/CONTEXT.md` says clients must be pre-registered and arbitrary dynamic registration is unavailable. **Current owning code also exposes `POST /oauth/register`** (`B/routes/mcp.php:18236`), and `B/app/Http/Controllers/Api/McpClientRegistrationController.php` supports public authorization-code/refresh clients with `token_endpoint_auth_method=none`, loopback HTTP or explicitly allowed HTTPS redirect hosts (`:130-146`). `B/app/Services/Mcp/McpClientRepository.php` accepts active sidecar registrations or configured preregistered clients. Therefore do not repeat “no dynamic registration” as an established current-code fact. This is constrained registration, not arbitrary callback acceptance; actual production enablement/configuration is unverified. A Jali callback client and exact registered redirects must be established through the approved deployed path before use. No client was registered here.

## Smallest concrete implementation options

**Option A — per-user runtime/execution isolation:** keep the stock Felix runtime contract, but give each JALA user a separate instance/container/workspace, Contact credential, and downstream MCP transport credential; do not mount another user's workspace or a shared privileged credential. The app backend routes only to the authenticated user's runtime. Add a server-side per-user MCP consent/token lifecycle integration (the built-in registry alone does not persist/refresh OAuth grants), plus provisioning and artifact routing. This avoids rewriting Felix's shared-workspace model, at the cost of operating multiple runtimes. It is not the already-confirmed single independent Jali runtime as originally envisaged and requires a product/operations choice. A common harmless image/skill baseline is compatible; shared writable customer data/secret mounts are not an isolation boundary.

**Option B — shared control plane, isolated workers and user-aware broker:** retain one app-facing Jali service, extend trusted routing to derive tenant identity from the authenticated API Contact, select upstream OAuth grant/transport by tenant (including discovery, resources, prompts, subscriptions and reconnect), and enforce tenant-specific capability visibility. Store/refresh/revoke OAuth grants outside model-readable files/env. Bind every worker to that identity and provide isolated filesystem/process/provider state/artifact access, with broad tools restricted to its own worker. Do not trust user-supplied MCP arguments or `_meta` as the identity. This is code and deployment work, not config; adding only a token lookup leaves shared shell bypasses and cross-user artifacts unresolved.

**Option C — restricted tool-only backend:** a purpose-built chat executor/broker can expose JALA MCP as the authenticated user's grant and exclude general filesystem/shell tools or run those in isolated workers. This can reduce the required Felix changes, but narrows the confirmed “full available capabilities” requirement unless separately isolated broad execution is included. Do not silently substitute it.

For either viable broad-tool route, acceptance must include two users with disjoint farms, denied cross-user session/artifact lookups, denied access to each other's execution files/credentials, correct simultaneous/reconnected MCP identity, revocation/refresh/expiry, existing JALA write policies and destructive-confirmation behavior. This is the minimal verification implied by the missing boundaries, not an invented new JALA permission policy.

## Limits and decision required

No deployment, proxy, application feature or credential was changed. Source review resolves the factual question: current Felix does not satisfy the shared-runtime per-user downstream authorization/isolation requirement through configuration alone. Choose isolation architecture or explicitly change capability scope before treating the integration as deployment-ready. OAuth registration deployment parity and authenticated Next ingress remain verification tasks; neither resolves the Felix isolation blocker by itself.
