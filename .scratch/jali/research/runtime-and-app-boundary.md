### Felix owner and app-user authentication are separate

Verified release sources:

- [v0.6.1 server auth](https://github.com/frdteknikelektro/felix-agent/blob/040ece747aa90b8ff360c411a6eb6a7a8f5ba279/src/server/app.ts): `POST /api/login` validates `OWNER_UI_SECRET` and creates an Owner session cookie. Ordinary private `/api/*` routes authenticate that cookie. `/v1/*` instead authenticates `Authorization: Bearer <Felix API key>`. Owner cookies alone do not authenticate `/v1`; API keys do not gain Owner authority.
- [v0.6.1 Contact/key routes](https://github.com/frdteknikelektro/felix-agent/blob/040ece747aa90b8ff360c411a6eb6a7a8f5ba279/src/server/routes.ts): create Contact using `POST /api/contacts/api/{contact_id}`; update using PUT. Provision its credential through GET/POST/PUT/DELETE `/api/api-keys/{contact_id}` for metadata/create/rotate/revoke. These sit behind Owner authentication. This is an Owner-admin interface, not public self-registration or a scoped app-provisioner credential.
- [v0.6.1 key contract](https://github.com/frdteknikelektro/felix-agent/blob/040ece747aa90b8ff360c411a6eb6a7a8f5ba279/docs/agents/felix-api-keys.md): one active key per API Contact; plaintext is revealed only on create/rotate; later reads return metadata. Rotation preserves Contact identity/grants, revocation affects subsequent admissions, and blocked Contacts cannot authenticate. A provisioning response lost after success requires deliberate recovery/rotation rather than assuming a safe retry. API keys are separate from model-provider credentials.
- [v0.6.1 durable sessions](https://github.com/frdteknikelektro/felix-agent/blob/040ece747aa90b8ff360c411a6eb6a7a8f5ba279/docs/agents/api-sessions.md): `/v1` sessions run the configured harness as the authenticated Contact; identity is `api:<contact_id>:<session_id>`. Other Contacts receive 404 for that Contact’s session resources. The owner can inspect API threads. Pending permissions require the real Owner approval flow; API clients cannot approve themselves. Admission or idle state alone does not mean success; inspect turn status/error. The documented tested SDK is `openai@7.27.0`; do not assume arbitrary SDK versions are compatible.

Per-user Contact identity isolates the documented API resource lookup. It does not establish separate runtime workspaces, separate harness credentials, or a guarantee that arbitrary custom Skills safely segregate all JALA customer data. Those need separate design and validation.

## Connection design — confirmed identity choice, proposed implementation

The user subsequently confirmed existing JALA login and per-user Contacts/API keys. This confirms the identity boundary; backend proxy versus direct access and provisioning method still require decisions.

1. **App backend with per-user Felix Contacts (proposal consistent with confirmed identity).** A trusted server authenticates the JALA session, derives a stable mapping such as `jala_user_<id>`, and authorizes every session, turn and artifact request for that user. Store Felix keys only in server-side secret storage and forward `/v1` requests with the corresponding Contact key. Initially provision Contacts/keys manually through Owner Console. This preserves the currently supported privilege boundary and needs no new Felix self-registration API. Intended audience and volume decide whether manual onboarding is sufficient.
2. **Automated provisioning using existing Owner interfaces.** A tightly isolated provisioning service can technically log in with the owner secret and call Contact/key `/api` routes. It carries broad Owner privilege; it is not a narrowly scoped provisioning API. Cookie lifetime, reauthentication, concurrent provisioning, lost one-time key responses and audit controls need explicit design. Do not give this secret/cookie to browsers or to ordinary per-user request handlers by default.
3. **A dedicated scoped provisioner extension.** Add a supported restricted service credential/API to Felix if automatic multi-user onboarding is required. This is additional implementation, not a feature demonstrated in v0.6.1.
4. **One shared app Contact/key.** Simpler operationally, but Felix sees one Contact and does not enforce JALA-user separation between its sessions. The app must implement all ownership isolation. It is unsuitable as an assumed per-user authorization design without accepting this limitation.

For any option, connecting Jali to JALA data is a separate downstream authorization decision. Select explicit per-user MCP consent or another reviewed backend delegation contract; never put one privileged shared JALA token into a multi-user agent and infer farm access from prompt text. Token/session expiry, disconnect, key rotation, request idempotency, stream reconnect, quotas and artifact authorization belong in the eventual integration acceptance plan.
